# SquadSpeak specification

The product contract is defined by the numbered requirements and confirmed user decisions below. Later decisions supersede earlier ones only where explicitly stated. Implementation and release status live in [the roadmap](../roadmap.md); measurements and previous runs live in [verification](../verification.md).

SquadSpeak is a compact C++/Qt voice and channel-chat application. Desktop comes first; mobile retains the agreed free feature set within demonstrated OS capabilities. A device's hosting service is independent of its personal participation. The host is a trusted decrypting endpoint. Free use remains possible without an Internet service or purchase.

## Confirmed decisions and provenance

| U4 | Antworten auf die drei Auswahlfragen nach U3 | Freunde stammen aus macOS-Kontakten; Auto-Beitritt wird pro Channel eingeschaltet; bei automatischem Beitritt wird immer der bisherige Stummzustand wiederhergestellt. |

| U16 | Änderung zu OS-Nutzung und Zugang nach U15 | Nur benötigte OS-Dienste, beispielsweise sichere Secret-Speicherung. Kontakteabgleich wird durch Host-Anfragen ersetzt. Anfragen standardmäßig eingeschaltet; Host bestätigt/lehnt ab und speichert die Entscheidung. Wiederholungen verlängern die Wartezeit; Client sieht diese. Spam wird sofort automatisch abgelehnt, ohne Host-Benachrichtigung. |
| U17 | Gleiche Nachricht, Bilder und Verschlüsselung | Jeder sendende Client entfernt Bildmetadaten durch Dekodieren und Neuerzeugen vor dem Versand an den Host; Transparenz bleibt erhalten, PNG ist ein genanntes Beispiel. Gruppen-E2E muss alle berechtigten Empfänger erreichen; der Host hält neben Client-Referenzen den nötigen Verschlüsselungszustand. |
| U18 | Gleiche Nachricht, Channel-Auswahl und Wiederherstellung | Der Vorschlag zur Channel-Auswahl wird angenommen: ein aktiver Sprachchannel, zuletzt gewählten Auto-Beitritt-Kandidaten bevorzugen, manuelles Verlassen beendet automatische Beitrittsversuche. Immer den letzten Zustand wiederherstellen; der Vorschlag, eine vorherige PTT-Freigabe grundsätzlich nicht wiederherzustellen, wird abgelehnt. |
| U19 | Gleiche Nachricht, Audio und mobile Grenzen | Eingangspegel und Frequenzen sichtbar machen, Frequenzen manuell filtern, dynamische Hilfe zur geschätzten Hauptstimme anbieten. Rausch- und Echounterdrückung sind Optionen. Sprachaktivierung erhält einen sichtbaren, manuell und automatisch verstellbaren Schwellwert. Mobile OS-Grenzen durch geeignete Lösungen berücksichtigen; eingeschaltetes Display ist ein zu untersuchender Vorschlag. |
| U20 | Antworten auf die Rückfragen nach U19 | Bei ausgeschalteten Anfragen dürfen nur bereits bestätigte Clients beitreten. Neue bestätigte Teilnehmer erhalten auch die noch gültige 24h-Historie. | U21 | Antwort zur autonomen Historienfreigabe | Der Host darf Chat-Schlüssel selbst verwalten und an neu bestätigte Clients weitergeben. Damit ist er ausdrücklich ein vertrauenswürdiger Endpunkt, der Inhalte technisch entschlüsseln kann, auch ohne Teilnahme seines Besitzers. |
| U22 | Ergänzung zu Vorabfreigaben nach U21 | Ein Host kann andere Hosts beziehungsweise deren Geräte ohne vorherige Anfrage für seinen Channel bestätigen. Vorab bestätigte Clients benötigen beim Beitritt keine Anfrage. |

| U24 | Antwort zur Veröffentlichungsform | Das Projekt soll Open-Source-Software werden. Eine konkrete Lizenz ist noch nicht gewählt. |
| U25 | Ergänzung zur kommerziellen Nutzung nach U24 | Wenn jemand die Software nutzt, um Geld zu verdienen, möchte der Nutzer daran mitverdienen. Vorrang gegenüber dem OSS-Ziel, erfasste Nutzungsfälle und Art/Höhe einer Beteiligung sind noch nicht geklärt. |
| U26 | Priorisierung nach U25 | Die Lizenz soll später entschieden werden. Vorrang hat die Fertigstellung der App; die zurückgestellte Lizenzfrage soll den Entwicklungsfortschritt nicht aufhalten. |
| U27 | Rückmeldung zur Frequenzanzeige und anschließender Vorbereitungsauftrag | Die bisherige Frequenzanzeige ist unzureichend verständlich. Verfahren aus Internetquellen recherchieren und die Analyse vorbereiten; der Nutzer ist währenddessen nicht am Computer. Daraus folgt keine Freigabe offener Automatik- oder PTT-Konfliktregeln. |
| U28 | Präzisierung des Bedienziels nach U27 | Kleine, leistungsfähige App für Nutzer ohne Audiowissen. Gut definierte Arbeiten, die keine manuellen Tests benötigen, sollen weitergehen. Hörtests bleiben dort nötig, wo automatische Nachweise nicht ausreichen. |

Andere Konzepte dürfen vorgeschlagen, anhand von Internetquellen untersucht und sinnvoll kombiniert oder ausgewählt werden. Maßstab bleibt eine kleine, leistungsfähige App für Einsteiger; daraus folgt keine Festlegung auf eine bestimmte Fremdsoftware oder Audioverarbeitung. |
| U30 | Umsetzungserlaubnis und Ergänzungen nach U29 | Bedienentwurf grundsätzlich bestätigt; selbstständig iterativ implementieren und bei fehlenden Spezifikationen fragen. "So viel wie möglich" bezeichnet eine Optimierungsrichtung, keine zugesicherte
unbegrenzte Kapazität oder universelle Geräteunterstützung. Bestätigte Grenzen
stehen in den Anforderungen; Empfehlungen gelten nicht als Zustimmung.
Der vorgeschlagene Vergleich der Mikrofonlautstärken ist eine zu prüfende
Lösungsidee, kein bereits ausgewählter Algorithmus.

The `udp-audio` capability keeps signaling and admission on pinned TLS and binds
the DTLS fingerprint to that session. Opus RTP uses the host's existing service
port number over UDP, independently for each admitted connection. Blockage falls
back to bounded TLS audio; recovery restores UDP. Legacy peers retain baseline
voice/chat. Reordering, replay rejection, source-slot reuse and Opus concealment
must be bounded. No external discovery or relay service is required.

The optional `udp-screen` capability carries the existing encoded frames through
an unordered, partially reliable WebRTC DataChannel (SCTP/DTLS/UDP). It shares
the authenticated endpoint, not audio's queue. This codec-independent path keeps
both H.264 and the portable MPEG-4 fallback. No native RTP video interoperability
is promised. Datagrams are limited to 16 KiB, SCTP send/receive buffers to 256 KiB,
and the application send backlog to 32 KiB plus one datagram. Packets expire after
100 ms. The receiver assembles one frame, bounded to 2 MiB plus 32 KiB metadata.
Lost frames expire at the next one-second maintenance pass after one second;
the following frame must be a keyframe. Decode acknowledgments use the same
UDP path, with TLS fallback. Legacy or UDP-blocked peers retain the existing
bounded TLS screen transport. Adaptation and voice priority remain per receiver.

## Technical limits

These are current implementation contracts with public tests, not claims of universal performance.

Die technischen Stufen sind 3840x2160/30 bei 12 Mbit/s, 1920x1080/30 bei
4 Mbit/s, 1280x720/15 bei 1,5 Mbit/s und 640x360/8 bei 350 kbit/s.
Das sind Obergrenzen/Zielbitraten, keine garantierten Empfangswerte; Seitenverhältnis
und kleinere Quellen bleiben erhalten. Eine reine Vorschau fordert höchstens die
kleinste Stufe an. Der große Betrachter beginnt höchstens bei 1080p und kann
nach stabiler Erholung auf UHD steigen. Drei schlechte Empfangs-/Decodierproben
senken eine Stufe; zehn stabile Sekunden erlauben einen Aufstieg. Nach Überlastung
der kleinsten Stufe pausiert Video und versucht nach drei Sekunden einen
Wiedereinstieg. Bestehende Audio-Engpasssignale und gemessene Encoder-Arbeit
lösen ebenfalls eine Reduktion aus. Ein einzelner langsamer Empfänger ändert
nicht die Stufe anderer Empfänger.

Je Zuschauer bleibt höchstens ein komprimiertes Bild mit maximal 2 MiB
unbestätigt. Der UDP-Pfad folgt den Grenzen oben; der TLS-Ersatzpfad schreibt
begrenzte 16-KiB-Blöcke und hält die Schreibwarteschlange klein. Codec-Instanzen werden pro benötigter Qualitätsstufe geteilt,
nicht je Zuschauer angelegt. Der Encoder nimmt höchstens sechs noch nicht
abgeholte Frames an und reduziert bei Überlauf den Bedarf. Es gibt keine
Aufzeichnung. Die Oberfläche zeigt die zuletzt empfangenen Abmessungen und
eine Lastpause. Qt verwendet denselben FFmpeg-Bestand wie der direkte Codec-Pfad;
unter macOS kommen passende Header aus dem gepinnten Quellenmanifest hinzu,
keine zweite Laufzeitbibliothek.

Prüfung beim Start und alle 15 Minuten; bei vorübergehenden Fehlern erfolgt
Rücknahme auf eine Minute bis eine Stunde Abstand. Die vorher bestätigte Laufzeit
bleibt bei Netzfehlern erhalten. Ablauf und bestätigte Ablehnung beenden die
Avatar-Freischaltung ohne Profiländerung. Der Ablauf wird auch bei einem wartenden
Netzaufruf oder belegter Speicherdatei gemeldet. Fehlgeschlagene lokale Änderungen
werden erneut gespeichert, solange die Datei weiterhin dem zuletzt gelesenen
Stand entspricht. Hat inzwischen eine andere Instanz beispielsweise einen neuen
Jahrespass gespeichert, wird deren neuer Stand übernommen. Eine erfolglose
Sperrspeicherung darf weder den unveränderten alten Nachweis wieder aktivieren
noch eine neuere Verlängerung überschreiben. Bei dauerhaft
nicht beschreibbarem Speicher bleibt die Sitzung ohne Extras. Ein Neustart kann
eine nie dauerhaft gespeicherte Sperre erst nach erneutem Anbieterkontakt erkennen.
Mehrere gleichzeitig laufende Profile übernehmen fremde Lizenzänderungen beim
nächsten Check, spätestens im regulären 15-Minuten-Intervall bei gesundem Speicher
und Netz. Kopiersicherheit gegenüber verändertem Programmcode oder Systemzeit
ist weiterhin keine zugesagte Eigenschaft.

Bilder nach U51: Dateien und kodierte Rasterdaten aus der Zwischenablage
bleiben beim Sender begrenzte, nicht dekodierte Quelldaten. Es gibt vor dem
Versand keine Dateivorschau. Liefert das OS ausschließlich ein bereits
gerendertes Zwischenablage-Bitmap, wird dieses für die Übertragung als PNG
kodiert. Ausschließlich der Host führt die Bereinigung im separaten
Decoder-Prozess aus. Rasterformate PNG, JPEG, WebP,
GIF und BMP sind anhand ihrer Signatur zugelassen; ein animiertes Quellbild wird
als erstes Einzelbild übertragen. Obergrenzen sind 25 MiB Quelle, 8192 Pixel
je Seite, 24 Megapixel und 8 MiB bereinigtes PNG. Neue Pixel enthalten keine
übernommenen Metadaten; Transparenz und angewandte Orientierung bleiben erhalten.
Der separate Prozess hat 20 Sekunden Laufzeit und eine Qt-Decodiergrenze von
128 MiB. Dies ist Prozessisolation mit Grenzen, keine OS-Sandbox oder Garantie
gegen unbekannte Decoderfehler. Empfänger prüfen Transfer-Prüfsumme,
PNG-Struktur, Größen und Host-Metadaten und rendern die unveränderte bereinigte
Kopie zur Anzeige. Sie führen keine zusätzliche Neukodierung aus. Ein
veränderter Sender umgeht die Host-Bereinigung nicht. Originaldaten sind
niemals der Fehler-Fallback.

Anhänge werden in bestätigten Blöcken von höchstens 16 KiB übertragen und beim
Host getrennt vom Text verschlüsselt gespeichert (TTL-gesteuerter Speicher,
32 MiB entschlüsselter Bildcache). Gemeinsam über alle eigenen Channels sind
höchstens vier Bild-Uploads gleichzeitig in Bearbeitung. Ein vollständiges Bild
wird erst nach Bereinigung und atomarer Speicherung als Nachricht bestätigt.
Ablauf entfernt zugehörige nicht mehr referenzierte Dateien; fehlende/defekte
Dateien werden als Fehler angezeigt.

Passwortzugang: Der Host speichert einen zufällig gesalzenen PBKDF2-HMAC-SHA256-
Prüfwert mit 600000 Iterationen. Client-Passwörter werden nur nach erfolgreichem
Beitritt und auf Wunsch gespeichert, getrennt pro bestätigter Host-Identität.
AES-256-GCM schützt diese Einträge; HKDF trennt den aus der OS-Geräteidentität
abgeleiteten Schlüssel vom Chat-Schlüssel. Vergessen entfernt den gespeicherten
Eintrag und erhält die aktuelle Verbindung. Das Passwort wird ausschließlich
über die geprüfte TLS-Verbindung übertragen, nicht über die Netzwerksuche.
Fehlversuche erhalten steigende, hostseitig gespeicherte Wartezeiten von
30 Sekunden bis 10 Minuten. Höchstens zwei Passwortberechnungen laufen parallel
außerhalb des Audio-/UI-Ereignisfadens. Kurzzeitige Auslastung löst einen zeitversetzten automatischen
Versuch aus; falsche Passwörter lösen keine automatische Wiederholung aus. Passwortänderungen während einer offenen Gerätefreigabe müssen vor
Zutritt erneut erfüllt werden; laufende Teilnehmer werden dabei nicht getrennt.

Terminal TLS replies revoke admission immediately. After consuming a final
join/control/video decision, the receiver closes its connection. The sender
keeps draining transport input without executing further commands; the existing
maintenance timer removes non-closing legacy peers after five seconds. Such
peers remain counted against pending-admission limits and cannot refresh this
deadline, regain admission or keep image/relay work alive. Normal disconnection
and terminal replies share membership/key-rotation cleanup. This adds no wire
message or mandatory capability; pending approval/password negotiation stays open.

Speech activation evaluates 20 ms frames, with 40 ms pre-roll and 300 ms hangover. Manual threshold range is -80 to 0 dBFS; moving it disables its automation until explicitly re-enabled. Rumble/gain automation and real acoustic echo cancellation are not implied by this threshold.

Release version resolution is shared by CMake and CI: UTC YYYY.M.D with no leading zeroes, for example 2026.10.4. This is calendar versioning with SemVer-compatible numeric syntax, not a promise that the year represents API compatibility. All jobs in a release use the same resolved value. Existing release tags are not overwritten; another release on the same UTC day currently fails rather than replacing reviewed packages.

## Acceptance scenarios

Cross-platform product acceptance is incomplete. Current automated evidence is mapped in the roadmap; OS permissions, physical acoustics and mobile lifecycle require separate proof.

Under U138, the maintainer owns setup, automation and analysis. The offline
device handoff and reuse rules are described in [development](../development.md#device-checks-with-limited-human-time).
The Windows tester has no on-site assistance: provide a packaged app, an isolated
two-instance launcher, exact connection instructions and a result file. Prepare
the transfer from macOS before the visit; building or debugging on the test PC
is not part of human acceptance.
An unchanged observation may be carried forward with its original tested build;
it must not be described as a new test of the current binary. Shared source or
runtime changes conservatively reopen affected observations. Synthetic media,
native virtual devices and CI packages remain the default proof for behavior
that does not intrinsically need hearing or physical hardware.
